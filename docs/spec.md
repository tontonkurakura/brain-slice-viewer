# 3D 脳モデルに MRI 断面を重ねる

3D の脳モデルを断面で切って、その切り口に MRI と領域色を出すための実装一式。

`viewer.html` をブラウザで開けば動く。ビルド手順もサーバーサイドも無い。
コードを読む前に、一度動かしてスライダーを動かしてみたほうが早い。

公開しているもの: <https://tontonkurakura.github.io/brain-slice-viewer/viewer.html>

```bash
cd <このディレクトリ>
python3 -m http.server 8791
# http://127.0.0.1:8791/viewer.html
```

---

## 1. 中身

| ファイル | 中身 |
|---|---|
| `viewer.html` | 本体。HTML・CSS・JS が 1 ファイルに収まっている |
| `brain.glb` | DKT アトラスのモデル。93 領域。頂点は world RAS (mm) |
| `brain_arterial.glb` | 血管支配アトラスのモデル。32 領域。切り替えたときに読む |
| `assets/<面>/t1_atlas.webp` | MRI 断面 256 枚を 1 枚に敷き詰めたもの。アトラス間で共有 |
| `assets/<面>/label_atlas.webp` | 領域色の断面（DKT） |
| `assets/<面>/label_atlas_arterial.webp` | 領域色の断面（血管支配） |
| `assets/slice_metadata.json` | 各面のスライス座標、タイルの並び、軸の向き。`atlas.labels` にアトラスごとのラベル画像 |
| `labels.json` | 領域名の日英、大分類、色、代表スライス（`slice`。world RAS mm）、`atlas`、`side`（`"L"`/`"R"`、正中は持たない）、`ja_short`/`en_short`（左右を外した名前）、`merge`（左右で 1 つとして扱う印） |
| `vendor/three/` | three.js r163、無改変（MIT）。外部を読まないので回線なしで開ける |
| `docs/spec.md` | この文書 |

資産（`*.glb`・断面画像・`labels.json`）を作る Python コードは、この配布パッケージには
含めていない。生成側リポジトリの `brainslice` パッケージが、`coords.py` の座標定義に
従って一括で書き出している。以下に出てくる `python -m brainslice.*` はそれのこと。

## 2. 座標系

world RAS（ミリ単位、+X が右、+Y が前、+Z が上）だけを使う。

* メッシュの頂点座標
* 断面板を置く位置
* クリップ平面の位置
* 断面画像のスライス番号

この 4 つは同じ数値なので、座標変換のコードが存在しない。冠状断を y = −20.1 mm に
出す場合はこうなる。

```
スライス番号   slice_metadata.json の planes.coronal.world_coords から -20.1 の添字を引く
貼るタイル     その添字のタイル
断面板の位置   y = -20.1
クリップ面     y = -20.1
```

変換式を書きたくなったら、たいていどこかで別の座標系が混ざっている。

### 経緯

前身の実装では 3D モデルが表示用にスケール・センタリングされていて、断面と
突き合わせるための変換が要った。その変換を「モデルの外形と画像ボリュームの外形を
一致させる」近似で作っていたため、

* 3 軸すべてで 3〜6% のスケール誤差
* 前後軸は符号が表現できず、約 165mm のずれ（前頭極を選ぶと後頭部が出る）

が生じていた。しかも画面上は断面が動いているようにしか見えないので、神経解剖を
知らなければ気づけない。座標系を 1 つに畳むと、この種のずれはそもそも表現できない。

### Y-up について

glTF は +Y を上とする慣習だが、頂点を回転させて焼き込むと上の前提が崩れる。
表示の向きはカメラ側で合わせる。

```js
camera.up.set(0, 0, 1);   // 頂点は触らない
```

## 3. 断面を出す

`viewer.html` の該当箇所を読むのが早いが、要点は 3 つ。

### (1) スライダーの値を実在するスライスに丸める

`slice_metadata.json` の `planes.<面>.world_coords` に、実在するスライスの world 座標が
並んでいる。連続値はこの中の最近傍に丸める。丸める前の値に断面板を置くと、画像と板が
最大 0.5 ボクセルずれる。

### (2) 断面画像はアトラスで持つ

全スライスを 1 枚の大画像に敷き詰めてある（256 枚 → 16×16 のタイル、4096×4096）。

1 枚ずつ取りに行く作りにすると、ホイールを速く回したときに読み込みが追いつかず、
断面が前の画像のまま滑る。「読み終わるまで前の画像を出す」といった小細工では症状が
変わるだけで、めくるたびに取りに行くこと自体を変えないと直らない。

アトラスなら最初に一度読むだけで、以降のめくりは UV オフセットを変えるだけになる。
GPU 上のデータは動かないので読み込み待ちが発生しない（実測で 200 枚連続 0.0ms、
1 枚あたり 0.000ms）。

タイルの並びは `index = row * cols + col`（左上から右へ、行は下へ）。`index` は
`world_coords` 配列の添字と一致する。three.js は既定でテクスチャを上下反転して読むので、
v 方向は入れ替えて計算する。

```js
tex.repeat.set(1 / cols, 1 / rows);
tex.offset.set((i % cols) / cols, 1 - (Math.floor(i / cols) + 1) / rows);
```

画像形式は WebP。T1 は表示用なので不可逆（品質 88）だが、ラベルは可逆でなければ
ならない。画素の色から領域を逆引きするため、圧縮で色が 1 でもずれると別の領域として
解決されてしまう。

| | PNG | WebP | 検証 |
|---|---|---|---|
| T1 | 5.0 MB | 0.90 MB | 見える画素の平均誤差 1.75/255、透過は完全一致 |
| ラベル | 0.79 MB | 0.34 MB | 全画素完全一致（色 53 種、差分 0） |

必要なテクスチャサイズは 4096。実機の上限は `gl.getParameter(gl.MAX_TEXTURE_SIZE)` で
分かる（デスクトップ GPU はたいてい 8192 以上）。足りない環境向けには、生成時に
アトラスを分割する必要がある。

### (3) 断面板とクリップ平面は同じ値から動かす

別々に計算すると必ずずれる。

```js
const w = snap(plane, sliderValue);   // ← 唯一の情報源
layoutPlane(plane, w);                //    断面板もクリップ平面もここから
```

### ホバーによる領域表示

判定は表示中の断面だけを見て、3D メッシュへのレイキャストは行わない。皮質表面は
開いた面で、その内側に皮質下構造や白質のメッシュが入れ子になっている。レイが最初に
当たる面が見た目の最前面と一致しないので、表面を指しているつもりで皮質下構造を拾う。

断面上の判定は、板に当たった点の UV からラベル画像の画素を読んで色で逆引きする。
ただし FreeSurfer の LUT は左右の同名構造に同じ色を割り当てているため（95 領域に対して
色は 53 種）、色だけでは左右が決まらない。当たった点の world x の符号で判別する。
中央構造（脳幹・第三/第四脳室）は色が一意なので問題ない。

ホバー判定用のラベル画素は、表示中のタイル（256×256）だけを canvas に取り出す。
アトラス全体（4096×4096）を展開すると 1 断面で 64MB 使う。

### 引き出し線とパネル

線の起点はカーソル、パネルの位置は領域の代表点から決める。こうするとカーソルを領域内で
動かしてもパネルは動かず、線だけが動く。起点も代表点にすると線が固まって指している
場所が分からなくなり、パネルをカーソル追従にすると今度は揺れて読みにくい。

代表点には、重心に最も近い「その領域の画素」を使う。重心そのものだと C 字型の領域で
領域の外に出る。

代表点は解決後の領域名をキーに集計する。色でまとめると、LUT が左右に同じ色を使っている
せいで左右の海馬が 1 つの代表点を共有し、パネルが左右で同じ場所に出る。

パネルは 2 枚ある。**ホバーのパネル**は脳の外接矩形を画面に投影して、その外側へ置く。
アンカーが左寄りなら左、右寄りなら右。カメラを動かすと投影位置が変わるので、毎フレーム
再配置する。面積が大きく情報にならない領域（大脳白質・白質低信号域・CSF）には
パネルを出さない。

**選択のパネル**は領域ごとに 1 枚で、画面上端の帯に横へ並べる。左右のコントロールに
挟まれたここは、ふだん空いている。上端からは 36px 空ける。並べる順は画面上のアンカーの x 順にする。こうすると
引き出し線が交差しない——同じ高さから出た線どうしは、始点も終点も同じ順に並んでいれば、
どの高さでも x の差の符号が変わらないため交わらない。

線はパネルの**下辺**から出す。パネルが上にあるので、横から出すと回り込む形になる。
起点は領域の代表点、終点はパネルの下辺の、アンカーの真下に寄せた点。

表示中の断面にその領域が出ていなければ、パネルも出さない。線が引けないまま名前だけ
残しても、どこを指しているのか分からない。選択そのものは残るので、一覧の印で分かる。

並びきらないときは、英語名と大分類を落とす → 名前を小さくして折り返す → 段を足す、
の順に詰める。パネルの幅を抑えるには `box-sizing: border-box` が要る。content-box の
ままでは padding のぶんはみ出して、狭い窓でコントロールに重なる。

断面がモデルに隠れている場所でもパネルを出さない。裏側から覗いてパネルが出るのは
不自然なので、立体的に最前面にあるときだけ出す。この判定には注意が要る。`Raycaster` は
クリップ平面を見ないため、切り落とされて画面に出ていないメッシュにも当たる。そのままだと
切り落とした側の面を遮蔽物として数えてしまうので、当たった点がクリップで残る側にあるかを
自分で調べる。

```js
if (state.clip && clip.normal.dot(h.point) + clip.constant <= 0) continue;
```

### 操作の割り当て

| 操作 | 動作 |
|---|---|
| 左ドラッグ | 回転 |
| ホイール | 断面を 1 枚めくる |
| Shift + ホイール | 10 枚めくる |
| 中ボタンドラッグ（上下） | ズーム |
| Ctrl/⌘ + ホイール | ズーム |
| 一覧・断面・3D をクリック | その領域を選ぶ（もう一度で外す） |

左右のキーを持ちながら実体が 1 つ、という領域がある。脳底動脈は正中を走る 1 本の
血管で、`Left-BA` / `Right-BA` に分かれているのは元アトラスが半球で割っているため。
`labels.json` の `merge` が同じものは、**一覧に 1 行、選ぶと両方、パネルは 1 枚**にする。
アンカーは左右の代表点を **world 座標で**平均して 1 点にする（画面上で平均すると
値が視点に依存する）。脳底動脈では x ≈ 0 の正中に来る。

キー・ラベル ID・メッシュのノード名は左右のまま変えない。変えるとメッシュ・LUT・
断面画像の対応が崩れる。束ねるのは見せ方だけ。

選択は 3 つまで持てる。修飾キーは使わない——タッチでは押せないため、押した順に積む
方式にしてある。4 つ目を押すといちばん古いものが外れる。一覧から足したときだけ、
その領域の代表スライスへ移動する。

位置スライダーの両端には mm ではなく向きを出す（矢状断=左/右、冠状断=後方/前方、
軸位断=尾側/頭側）。`world_coords` は昇順なので、左端が負の側になる。

画面右上のコントロールは、断面の選択・位置・「領域色を重ねる」「モデルを断面で切る」・
「切る向きを反転」だけに絞ってある。濃さや不透明度を連続値で調整するスライダーは
置いていない。中間値に意味が無いうえ、操作が増えるほど今どういう状態なのかが分かりにくく
なるため。

画面の下には出典と注意書きを 1 行出す。血管支配アトラスが CC BY-SA なので、帰属表示は
画面の中にも要る。外部へのリンクは持たせていない（読み込みも行き先も持たない）。

操作子の形は 1 つに揃えてある。どれも同じボタンで、入っているものに `on`（青）が付く
（断面／立体、左／右、領域色を重ねる、皮質を表示、すべて同じ扱い）。チェックボックスは
使わない。その場で効く操作は「反転」だけで、これは幅を詰めて並べ、切っていないときは
押せなくしてある。アトラスの呼び名は画面では「解剖学領域」「血管支配領域」で、
DKT のような出自の名前は出さない。

ホイールをめくりに使う都合で、ズームは中ボタンと修飾キーに逃がしている。three.js の
`OrbitControls` は `enableZoom` がホイールと中ボタンを一括で止めるので、中ボタンの
ズームは自前で実装することになる。

### 画像の向き

`slice_metadata.json` の各面に `col_axis` / `row_axis` がある。

```json
"axial": { "normal_axis": "z", "col_axis": "+x", "row_axis": "-y" }
```

画像の列番号が増える向きが world の +x、行番号が増える向きが world の −y という意味。
行は画面下向きに増えるので、板のローカル上方向は `row_axis` の逆になる。ここを推測で
実装すると左右反転の発生源になる。

### 表示規約

既定は neurological（画像の左が患者の左）。3D モデルは常に解剖学的に正しい向きにあるので、
radiological（画像の左が患者の右）にするとモデルと断面で左右が食い違う。読影の習慣に
合わせたい場合は 3D 側も反転させる必要がある。

## 3b. 起動時のロード

めくりは読み込みゼロだが、起動時にはモデル（7.2MB）と断面アトラス（5.8MB）の読み込みが
要る（localhost で実測 520ms）。

* この 2 つは並行して読む。直列にすると待ち時間が足し算になる
* 最初の断面が出るまで操作を止める。断面が出ていない状態で触れると、何が起きているのか
  分からない
* 進捗はバイト単位で取る。分母が途中で増えると、バーが一度 100% に達してから落ちるので、
  全部の読み込みを開始してから集計する

残り 2 断面のアトラスは、最初の断面が出てから裏で読む。断面を切り替えたときの待ちが
無くなる。

## 3c. アトラスを差し替える／増やす場合

同梱しているのは DKT（Desikan-Killiany-Tourville、31/半球）と血管支配の 2 つ。

差し替えはこの設計では入力の差し替えでしかない。`export_slices.py` も `build_meshes.py` も
(ラベルボリューム, LUT) を受け取るだけで、どのアトラスかを知らない。座標の取り決めも
受け入れテストも変更は要らない。

一度 Destrieux（a2009s、74/半球）を追加して切り替え可能にしたが、細かすぎるという判断で
撤回した。そのときに踏んだものを残しておく。いずれも画面上はもっともらしく見えるのに
指している領域が違うという種類で、受け入れテストが無ければ気づかない。

**(1) `mri_aparc2aseg` は `--a2009s` を付けないと 1000 番台の ID を書く**

```
--a2009s なし  →  1000〜2075（ctx-lh-bankssts など DK の名前）
--a2009s あり  →  11100〜12175（ctx_lh_S_central など）
```

付け忘れると、Destrieux の annot から作ったはずのボリュームに無関係の DK 領域の ID が
入る。断面の色はもっともらしく出る。

**(2) FreeSurferColorLUT には紛らわしい重複がある**

```
1145   ctx-lh-S_central    ← 旧 a2005s 系（ハイフン）
11146  ctx_lh_S_central    ← a2009s（アンダースコア）
```

名前を組み立てて LUT を引くと前者を掴む。annot の索引から `ID = 先頭ID + 索引` で直接
計算する。

**(3) 除外する領域名の綴りがアトラスで違う**

DKT は `unknown`、Destrieux は `Unknown` と `Medial_wall`。大小・区切り文字を無視して
判定する。内側壁を取りこぼすと、半球の内側面に巨大な板状のメッシュができる。

**(4) 左右判別の接頭辞が違う**

DKT は `ctx-lh-`、Destrieux は `ctx_lh_`。片方だけ見ていると左右が入れ替わる。

**(5) T1 を共有する場合、差し替え判定に注意**

T1 の断面画像はアトラスに依存しないので共有できるが、「T1 のテクスチャが変わったら
ラベルも差し替える」と書くと、共有しているせいで条件が常に偽になり、ラベルが前のまま
残る。判定は両方の map を見る。

**(6) 領域数が増えると色による逆引きが破綻する**

現状ですら左右が同色で（DKT 95 領域に対して 53 色）、world x の符号で判別している。
数百領域規模のアトラスを足すなら、表示色とは別にラベル ID を符号化した画像を配る
設計変更が要る。

## 4. 既存の 3D モデルを使いたい場合

自前のモデルを使い続けるなら、やることは 1 つだけ。

> そのモデルの頂点を world RAS(mm) に揃えて、焼き直す。

表示用にスケール・センタリングされたモデルは座標系が定義されていない。それが
「断面が合わない」原因なので、そこを直せば以後は同じ前提に乗る。揃っているかどうかは
機械で判定できる。

```bash
python -m brainslice.check_alignment --seg <ラベルボリューム> --glb <あなたのモデル.glb>
```

```
[  OK  ] 一致: Left-Hippocampus   メッシュ重心とラベル重心の距離 1.8 mm
[ FAIL ] 一致: Left-Hippocampus   メッシュ重心とラベル重心の距離 34.2 mm
```

落ちればまだ揃っていない。ずれ量も出る。

## 5. 受け入れテスト

```bash
python -m brainslice.check_alignment --seg <ラベルボリューム> --glb brain.glb
```

| 種別 | 内容 |
|---|---|
| 向き | affine が RAS で軸平行か |
| 左右 | 左海馬・左扁桃体が `x < 0`、右が `x > 0`。左右の対称性 |
| 前後 | 上前頭回が外側後頭皮質より前 |
| 上下 | 中心傍小葉が脳幹より上 |
| 往復 | スライダー値 → ファイル名 → world 座標 が一致するか |
| 一致 | メッシュの重心とラベルボリュームの重心が 10mm 以内か |

最後の「一致」が本命で、ここが通れば断面画像とモデルは同じ座標系にいる。

左右の反転は目視では検出できないうえ、臨床で使うものとしては最も危険なバグなので、
「左海馬は x が負のはず」という数値条件に落としてある。これなら神経解剖を知らなくても
判定できる。

向きの扱いには別途単体テストがある。

```bash
python -m tests.test_orientation   # 格納方向によらず同じ画像になるか（12 項目）
```

## 6. つまずいた箇所

### GLB に法線が無いと真っ黒になる

trimesh の既定エクスポートは法線（NORMAL 属性）を含めない。glTF の読み込み側は法線が
無いと `flatShading` を立てて補うが、こちらがマテリアルを差し替えた時点でその指定が
失われ、法線ゼロで陰影計算されて全面が黒くなる。三角形が 648,320 個描画されているのに
画面は真っ黒という状態になり、原因の特定に時間がかかった。マテリアルを差し替えるなら
法線は必須。

```python
trimesh.exchange.gltf.export_glb(scene, include_normals=True)
```

### 断面板の背景が不透明だとモデルが消える

断面板はボリューム全体を覆う矩形（188mm 四方）なので、背景が不透明だとモデル全体を隠す
壁になり、切って中を見る表示が成立しない。背景の黒も不透明であることに変わりはない。
MRI 画像は脳の外を `alpha = 0` にして書き出してある。

### ボクセル添字の向きと world 座標の向きは一致しない

affine の対角成分が負なら逆になる。FreeSurfer の conformed 空間は LIA（軸の入れ替えと
符号反転）で、affine は対角にすらならない。読み込んだ直後に RAS+ へ正準化する。下流で
個別に向きを直そうとすると、必ずどこかで食い違う。

```python
img = nibabel.as_closest_canonical(nibabel.load(path))
```

### 領域ごとに簡約すると境界に隙間が開く

領域に切り分けてから個別に簡約・平滑化すると、隣り合う領域が共有していた境界の頂点が
別々に動き、間に隙間が開く。その隙間から内側のメッシュが覗く（白質は白いので白い線に
見える）。結合したまま削って、最後に分ける。簡約は分割前に全体へ掛け、ラベルは簡約後の
頂点へ最近傍で移す。分割後は頂点を動かさない。

### 切らないならレイキャストは素直に効く

断面モードで 3D への当たり判定をやめたのは、クリップ平面で消えたメッシュにもレイが
当たるため（`Raycaster` は `clippingPlanes` も `visible` も見ない）。モデルを切らない
立体モードではその前提が消えるので、レイの最初の当たりが深度バッファで勝つ面と一致する。

### ラベル画像を線形補間してはいけない

ラベルの画素値は領域の ID。補間すると存在しない領域の色が生まれる。

```js
tex.minFilter = tex.magFilter = THREE.NearestFilter;
```

## 8. 用語

| 用語 | 意味 |
|---|---|
| ボクセル | MRI の 3D 格子の 1 マス。画素の 3D 版 |
| world RAS | 実寸のミリ座標。`+X=右` `+Y=前` `+Z=上`。MNI 座標と同じ考え方 |
| affine | ボクセル番号 ↔ ミリ座標 の変換表。NIfTI/MGZ のヘッダに入っている |
| セグメンテーション | 各ボクセルに領域ラベル番号を振った 3D 画像 |
| メッシュ / GLB | 3D モデル本体（三角形の集まり）と、その標準ファイル形式 |
| marching cubes | ラベル画像から領域の表面を三角形として取り出す処理 |
| 表面パイプライン | 皮質の面をボクセルより細かい精度で推定する FreeSurfer の処理 |
| tkrRAS / `c_ras` | FreeSurfer 内部の原点がずれたミリ座標と、そのズレ量 |
| クリップ平面 | 「この面より手前は描かない」という 3D 表示の指定 |
| DKT | 皮質の区分法。片半球 31 領域 |
